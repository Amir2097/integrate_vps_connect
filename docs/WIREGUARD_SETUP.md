# Установка и настройка WireGuard на Ubuntu/Debian

Пошаговая инструкция для VPS (в т.ч. в Финляндии): установка сервера и настройка клиентов.

---

## 1. Требования

- VPS с **Ubuntu 20.04+** или **Debian 11+**
- Доступ по SSH (root или sudo)
- Открытый **UDP-порт** (по умолчанию 51820)

---

## 2. Установка WireGuard на сервере

Подключись по SSH к VPS и выполни:

```bash
# Обновление пакетов
sudo apt update && sudo apt upgrade -y

# Установка WireGuard
sudo apt install -y wireguard
```

Проверка:

```bash
wg --version
```

---

## 3. Генерация ключей сервера

```bash
# Переход в каталог WireGuard
cd /etc/wireguard

# Включение правильных прав (файлы ключей должны быть защищены)
umask 077

# Генерация ключей сервера
wg genkey | tee server_private.key | wg pubkey > server_public.key
```

Запомни или сохрани **приватный ключ сервера** (содержимое `server_private.key`):

```bash
cat server_private.key
```

---

## 4. Конфигурация сервера

Создай конфиг:

```bash
sudo nano /etc/wireguard/wg0.conf
```

**Пример конфигурации** (подставь свои значения):

```ini
[Interface]
# Приватный ключ сервера (из server_private.key)
PrivateKey = <СОДЕРЖИМОЕ_server_private.key>

# Интерфейс слушает на порту 51820
ListenPort = 51820

# Подсеть VPN. Не используй 10.0.0.0/24 — у многих VPS шлюз провайдера 10.0.0.1,
# будет конфликт маршрутов и пропадёт SSH (см. раздел 5.1).
# Имя интерфейса для NAT ниже — часто eth0 или ens3 (узнать: ip a)
Address = 10.66.0.1/24

# NAT и пересылка трафика в интернет
PostUp = iptables -A FORWARD -i wg0 -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

# --- Клиенты (peers) добавляются ниже ---
# Каждый [Peer] = один пользователь/устройство
```

**Важно:** замени `eth0` на твой исходящий интерфейс (`ip a` или `ip route` — там будет dev eth0, ens3 и т.п.).

Включи IP-форвардинг (сохраняется до перезагрузки):

```bash
echo "net.ipv4.ip_forward=1" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

Запуск и автозапуск:

```bash
sudo systemctl enable wg-quick@wg0
sudo systemctl start wg-quick@wg0
sudo systemctl status wg-quick@wg0
```

Проверка интерфейса:

```bash
sudo wg show
```

---

## 5. Открытие порта в файрволе

**Важно:** если включишь UFW, не открыв заранее порт **22 (SSH)**, ты потеряешь доступ к серверу. Сначала разреши SSH, потом WireGuard, и только потом включай файрвол.

**UFW:**

```bash
# Сначала обязательно разреши SSH — иначе после ufw enable потеряешь доступ
sudo ufw allow 22/tcp
sudo ufw allow 51820/udp
sudo ufw enable
sudo ufw status
```

**iptables** (если не используешь UFW) — правило FORWARD и MASQUERADE уже заданы в PostUp выше; убедись, что входящий UDP 51820 не блокируется.

## 5.1 Если после настройки пропал SSH (заблокировался доступ)

Восстанавливай доступ через **VNC / Web Console** в панели хостера, затем проверь по очереди.

### Причина A: Конфликт подсети с шлюзом провайдера

Если в инструкции использовалась подсеть **10.0.0.0/24**, а у хостера шлюз по умолчанию — **10.0.0.1** (часто бывает у VPS), то после поднятия WireGuard маршрут по умолчанию «сливается» с адресом твоего VPN-интерфейса. В итоге весь трафик (в т.ч. ответы SSH) уходит не туда. В консоли `ip route` покажет что-то вроде:

```text
default via 10.0.0.1 dev ens3 onlink
10.0.0.0/24 dev wg0 ...
```

**Что сделать в консоли VPS:**

1. Остановить WireGuard, чтобы вернуть нормальный default:
   ```bash
   wg-quick down wg0
   ```
2. Проверить маршрут: `ip route` — default должен быть через шлюз провайдера по `ens3` (или твоему интерфейсу), без wg0.
3. Подключись по SSH с ПК — должно заработать.
4. Поменять подсеть VPN на ту, что не конфликтует (например **10.66.0.0/24**):
   ```bash
   sudo nano /etc/wireguard/wg0.conf
   ```
   - В `[Interface]` замени `Address = 10.0.0.1/24` на `Address = 10.66.0.1/24`.
   - У всех `[Peer]` замени `AllowedIPs = 10.0.0.2/32` на `10.66.0.2/32`, `10.0.0.3/32` на `10.66.0.3/32` и т.д.
5. В конфигах клиентов (.conf) замени `Address = 10.0.0.2/24` на `10.66.0.2/24` (и т.д. по номерам клиентов).
6. Снова поднять WireGuard:
   ```bash
   sudo wg-quick up wg0
   ```
7. Ещё раз проверить: `ip route` — default по-прежнему через ens3 (не через 10.66.0.1 по wg0).

Дальше в инструкции используется подсеть 10.66.0.0/24, чтобы этого избежать.

### Причина B: UFW заблокировал порт 22

Если перед этим делали `ufw enable` без `ufw allow 22/tcp`, SSH режется файрволом. В консоли:

```bash
ufw allow 22/tcp
ufw reload
ufw status
```

После этого попробуй SSH снова.

## 5.2 Логика: кто что запускает и почему «не стыкуется»

### Цепочка при создании конфига через проект

1. **Пользователь в боте** нажимает «Подключиться» → админ в админке жмёт «Подтвердить».
2. **Бэкенд (процесс uvicorn)** — крутится от пользователя, например **amir** (или root, если в systemd указан `User=root`).
3. Бэкенд вызывает **скрипт** `/usr/local/bin/add-wg-client.sh` (напрямую или через `sudo`).
4. Скрипт **под root** (если через sudo) или под тем же пользователем:
   - читает и дописывает `/etc/wireguard/wg0.conf`;
   - создаёт файл `/etc/wireguard/clients/userN_M.conf`;
   - вызывает `wg syncconf` / `wg-quick strip`.
5. **Бэкенд потом сам** читает созданный файл (`conf_file.read_text()`) и отдаёт содержимое в БД и пользователю в Telegram.

Несостыковка: **скрипт создаёт файл от root** в каталоге, доступном только root. Если бэкенд крутится от **amir**, то после шага 4 процесс amir **не может прочитать** только что созданный конфиг (нет прав на `/etc/wireguard/clients/` и на файл 600). В итоге создание в шаге 4 проходит, а чтение в шаге 5 — нет (ошибка или «конфиг не создан»). Раньше конфиги «работали от root», потому что и скрипт, и сервис WireGuard работали в окружении root; при смене прав или пользователя цепочка рвётся.

Про порты и поддомен: в конфиге клиента в конец подставляется `Endpoint = SERVER_ENDPOINT:WG_PORT` (из `.env`: `SERVER_ENDPOINT`, `WG_PORT`). Порт должен совпадать с `ListenPort` в `/etc/wireguard/wg0.conf`. Если после смены прав или перезапуска сервис `wg-quick@wg0` не поднялся или поднялся с другим портом — туннели перестают работать. Поддомен «не встаёт», если DNS указывает на другой хост или порт закрыт файрволом.

## 5.3 Рекомендуемая схема: один из двух вариантов

### Вариант 1: Всё от root (проще всего)

Приложение и скрипт работают от **root**. Права в `/etc/wireguard/` не трогаем, ничего не ломается.

- **Плюсы:** одна учётная запись, скрипт и чтение конфигов без прав и sudo, порты и сервис как при ручной настройке.
- **Минус:** при компрометации приложения злоумышленник имеет права root.

**Шаги:**

1. WireGuard настроен как в разделе 4 (всё от root), права по умолчанию (700/600).
2. В systemd для бэкенда указать `User=root` (или не указывать — по умолчанию root).
3. В **.env**: `WG_USE_SUDO=false`, `WG_SCRIPT_PATH=/usr/local/bin/add-wg-client.sh`. Скрипт вызывается напрямую, без sudo.
4. Скрипт на сервере — тот же из репозитория; при вызове от root переменная `WG_SKIP_ROOT_CHECK` не обязательна (проверка root в скрипте пройдёт).

Проверка (от root):  
`/usr/local/bin/add-wg-client.sh testclient core.dautovtech.ru` — конфиг создаётся, бэкенд его прочитает и отдаст в бота.

---

### Вариант 2: Приложение от пользователя (amir), скрипт через sudo

Приложение крутится от **amir**, скрипт и команды `wg` выполняются **от root через sudo** без пароля. Чтобы бэкенд (amir) мог прочитать созданный конфиг, нужны **минимальные** права только на каталог с конфигами клиентов и на сами файлы.

- **Плюсы:** приложение не под root.
- **Минусы:** настройка sudoers и прав на один каталог.

**Шаги:**

1. **Права в `/etc/wireguard/`** (выполнить от root один раз):

   - Оставить `/etc/wireguard` и `wg0.conf` только для root (700 и 600).
   - Разрешить только **проход** в каталог и чтение **уже созданных** конфигов клиентов:
   ```bash
   sudo chmod 711 /etc/wireguard
   sudo chown root:root /etc/wireguard/clients
   sudo chmod 755 /etc/wireguard/clients
   ```
   После создания скриптом файлы в `clients/` должны быть читаемы для amir — см. шаг 4.

2. **Sudoers** — amir без пароля выполняет только скрипт и две команды wg:
   ```bash
   sudo tee /etc/sudoers.d/wireguard-amir << 'EOF'
   amir ALL=(root) NOPASSWD: /usr/local/bin/add-wg-client.sh
   amir ALL=(root) NOPASSWD: /usr/bin/wg syncconf wg0 -
   amir ALL=(root) NOPASSWD: /usr/bin/wg-quick strip wg0
   EOF
   sudo chmod 440 /etc/sudoers.d/wireguard-amir
   ```

   **Отзыв peer и удаление `.conf` из админки:** процесс приложения не читает и не пишет `wg0.conf` напрямую (файл обычно `600` у root). Без дополнительных прав команды «Заблокировать» / «Удалить конфиг» не меняют сервер. Рекомендуется один скрипт и одна строка sudoers:

   ```bash
   sudo cp /path/to/integrate_vps_connect/scripts/wg-backend-helper.sh /usr/local/bin/wg-backend-helper.sh
   sudo chmod +x /usr/local/bin/wg-backend-helper.sh
   sudo tee /etc/sudoers.d/wireguard-backend-helper << 'EOF'
   amir ALL=(root) NOPASSWD: /usr/local/bin/wg-backend-helper.sh
   EOF
   sudo chmod 440 /etc/sudoers.d/wireguard-backend-helper
   ```

   Положи `wg-backend-helper.sh` **в ту же директорию**, что и `add-wg-client.sh` (например оба в `/usr/local/bin/`), либо задай в `.env` явный путь `WG_HELPER_SCRIPT_PATH=/usr/local/bin/wg-backend-helper.sh`. Если интерфейс не `wg0`, укажи `WG_INTERFACE=wg1` в `.env`.

   В sudoers должна быть именно команда вида **«пользователь может выполнять этот исполняемый файл»** (`NOPASSWD: /usr/local/bin/wg-backend-helper.sh`). Бэкенд вызывает `sudo /usr/local/bin/wg-backend-helper.sh …` (**не** `sudo env …`), иначе sudo сверяет whitelist с другой командой и отзыв не работает.

3. **.env**: `WG_USE_SUDO=true`, `WG_SCRIPT_PATH=/usr/local/bin/add-wg-client.sh`. Systemd: `User=amir`.

4. **Скрипт после создания файла** должен выставить права так, чтобы amir мог его прочитать. В репозитории скрипт делает `chmod 600`; для варианта 2 нужен `chmod 644` созданного `.conf` (или скрипт может проверять переменную окружения и тогда делать 644). См. ниже правку в скрипте.

Проверка от amir:  
`sudo /usr/local/bin/add-wg-client.sh testfromamir core.dautovtech.ru` — пароль не запрашивается; затем бэкенд должен успешно прочитать созданный файл.

---

### Итоговая рекомендация

- Нужна максимальная простота и минимум возни с правами → **вариант 1 (всё от root)**.
- Нужно, чтобы приложение не работало под root → **вариант 2 (amir + sudo + минимальные права на `clients/`)**.

Порты и поддомен: в `.env` должны быть `SERVER_ENDPOINT=core.dautovtech.ru` и `WG_PORT=51820` (или тот порт, что указан как `ListenPort` в `wg0.conf`). После любых прав или перезапусков проверяй: `sudo wg show`, `sudo systemctl status wg-quick@wg0`.

## 5.4 Детали варианта 2: права и скрипт

Если WireGuard ты настраивал **под root**, то файлы в `/etc/wireguard/` по умолчанию недоступны пользователю **amir**. Скрипт при прямом запуске от amir не видит `wg0.conf`; при запуске через sudo скрипт создаёт конфиг, но процесс amir не может его прочитать без дополнительных прав.

При варианте 2 скрипт вызывается от root через sudo (запись в `wg0.conf` и создание файла в `clients/`), а **читать** созданный конфиг должен процесс приложения (amir). Поэтому:

- Скрипту не нужны права amir на запись: он работает от root.
- Нужно, чтобы amir **мог прочитать** каталог `clients/` и созданные там файлы. Для этого:
  1. Каталог `/etc/wireguard` — право прохода для остальных: `chmod 711` (чтобы amir мог обращаться по пути к файлу в `clients/`).
  2. Каталог `/etc/wireguard/clients` — чтение для остальных: `chmod 755`.
  3. Скрипт при вызове из приложения получает **третий аргумент `1`** (sudo не передаёт env), делает созданный файл читаемым: `chmod 644` (в репозитории это уже есть).

Список команд для варианта 2 (один раз от root):

```bash
# Sudoers: amir без пароля запускает только скрипт и две команды wg
sudo tee /etc/sudoers.d/wireguard-amir << 'EOF'
amir ALL=(root) NOPASSWD: /usr/local/bin/add-wg-client.sh
amir ALL=(root) NOPASSWD: /usr/bin/wg syncconf wg0 -
amir ALL=(root) NOPASSWD: /usr/bin/wg-quick strip wg0
amir ALL=(root) NOPASSWD: /usr/local/bin/wg-backend-helper.sh
EOF
sudo chmod 440 /etc/sudoers.d/wireguard-amir

# Минимальные права, чтобы amir мог только читать созданные конфиги (wg0.conf не трогаем)
sudo chmod 711 /etc/wireguard
sudo chown root:root /etc/wireguard/clients
sudo chmod 755 /etc/wireguard/clients

# Существующие конфиги в clients/ — сделать читаемыми для amir (один раз)
# Туннели от этого не пострадают: сервис wg0 читает только wg0.conf
sudo chmod 644 /etc/wireguard/clients/*.conf
```

В **.env**: `WG_USE_SUDO=true`, `WG_SCRIPT_PATH=/usr/local/bin/add-wg-client.sh`. Systemd: `User=amir`. Приложение вызывает скрипт с третьим аргументом `1` (например `sudo add-wg-client.sh user1_9 core.dautovtech.ru 1`), скрипт выставляет созданному файлу 644 — бэкенд (amir) успешно читает конфиг и отдаёт его в бота.

**Существующие конфиги и туннели:** при переходе на вариант 2 мы не меняем `wg0.conf` и не перезапускаем WireGuard с другими настройками — только права на каталоги и файлы в `clients/`. Работающие VPN-подключения **не упадут**. Файлы `.conf` в `clients/` на сервере нужны только для раздачи пользователям; после `chmod 644` на них приложение (amir) сможет их читать (повторная выдача, админка). Если не выполнить `chmod 644` для уже созданных файлов, старые конфиги по-прежнему будут работать у клиентов в телефоне/ПК, но бэкенд не сможет прочитать эти файлы (например, при «выдать конфиг повторно»).

**Проверка (обязательно после обновления скрипта на сервере):**

1. Скрипт на сервере должен быть **актуальной** версии из репозитория (с поддержкой третьего аргумента и `chmod 644`). Скопируй `scripts/add-wg-client.sh` в `/usr/local/bin/add-wg-client.sh` и сделай `chmod +x`.
2. Ручной тест с третьим аргументом `1` (под пользователем amir или root):  
   `sudo /usr/local/bin/add-wg-client.sh chmodtest core.dautovtech.ru 1`  
   Затем: `ls -l /etc/wireguard/clients/chmodtest.conf` — должно быть **-rw-r--r-- (644)**. Если по-прежнему **-rw------- (600)** — на сервере старая копия скрипта.
3. После деплоя бэкенда перезапусти сервис: `sudo systemctl restart vpn-manager` (или как у тебя называется unit). Затем проверь выдачу конфига через подтверждение оплаты в админке.

**Не рекомендуется:** менять владельца/права на `wg0.conf` и весь `/etc/wireguard` под группу wireguard — это часто ломает работу сервиса и приводит к запросу пароля у `wg-quick`.

## 6. Добавление клиента (peer)

### 6.0 Быстрый способ: скрипт + QR-код (рекомендуется)

В репозитории есть скрипт **scripts/add-wg-client.sh**: он создаёт ключи, добавляет peer в конфиг, сохраняет конфиг клиента и выводит QR-код в терминал.

**На сервере:**

1. Скопируй скрипт на VPS (например в `/root/` или `/usr/local/bin/`).
2. Установи генератор QR (один раз):  
   `sudo apt install -y qrencode`
3. Запуск (подставь имя клиента и свой IP или домен VPS):  
   `sudo ./add-wg-client.sh friend1 82.117.84.212`

Скрипт сам подберёт следующий свободный IP (10.66.0.2, 10.66.0.3, …), добавит peer в wg0, создаст файл конфига в `/etc/wireguard/clients/friend1.conf` и выведет QR-код в терминал. Открой приложение WireGuard на телефоне → «Добавить туннель» → «Сканировать QR-код» и наведи на экран.

**Сохранить QR в файл (чтобы отправить картинкой):**  
`qrencode -t png -o friend1.png < /etc/wireguard/clients/friend1.conf`  
Файл `friend1.png` можно скинуть в мессенджер.

**Переменная окружения вместо аргумента:**  
`export SERVER_ENDPOINT=82.117.84.212`  
`sudo ./add-wg-client.sh friend2`

---

Для ручного добавления клиента — шаги ниже.

### 6.1 Генерация ключей клиента

На сервере (или на своей машине):

```bash
# Приватный ключ клиента
wg genkey | tee client_private.key | wg pubkey > client_public.key

# Просмотр ключей
cat client_private.key   # — в конфиг клиента
cat client_public.key    # — в конфиг сервера
```

### 6.2 Добавление Peer на сервер

Открой конфиг сервера:

```bash
sudo nano /etc/wireguard/wg0.conf
```

В конец файла добавь блок (для каждого клиента — свой блок):

```ini
[Peer]
# Публичный ключ этого клиента
PublicKey = <СОДЕРЖИМОЕ_client_public.key>

# Опционально: общий секрет для пары сервер–клиент (доп. защита). Сгенерировать: wg genpsk
# PresharedKey = <СОДЕРЖИМОЕ_файла_или_вывода_wg_genpsk>

# Внутренний IP клиента в VPN (у каждого свой)
# /32 = «ровно один адрес» (этот peer — только 10.66.0.2). На сервере у [Interface] — /24 (вся подсеть).
AllowedIPs = 10.66.0.2/32
```

Если используешь PresharedKey — один и тот же ключ должен быть и на сервере в этом [Peer], и у клиента в [Peer]. Генерация на сервере: `wg genpsk` (результат подставить в оба конфига).

Можно добавить несколько клиентов с разными IP, например:
- Клиент 1: `10.66.0.2/32`
- Клиент 2: `10.66.0.3/32`
- и т.д.

Примени изменения без перезагрузки сервера:

```bash
sudo wg addconf wg0 <(wg-quick strip wg0)
# Или проще: добавить peer вручную:
# sudo wg set wg0 peer <PUBLIC_KEY_CLIENT> allowed-ips 10.66.0.2/32
```

Либо перезапусти интерфейс:

```bash
sudo wg-quick down wg0
sudo wg-quick up wg0
```

### 6.3 Конфиг для клиента

Файл, который человек ставит в приложение WireGuard (телефон/ПК). Пример:

**Структура:** блок `[Interface]` — настройки **этого устройства** (клиента). Блок `[Peer]` — **второй конец туннеля** (сервер). Поэтому ключ клиента — сверху, ключ сервера — в [Peer]. Так и должно быть.

```ini
[Interface]
PrivateKey = <ПРИВАТНЫЙ_КЛЮЧ_КЛИЕНТА>
Address = 10.66.0.2/32
DNS = 1.1.1.1, 1.0.0.1

[Peer]
PublicKey = <ПУБЛИЧНЫЙ_КЛЮЧ_СЕРВЕРА>
Endpoint = <IP_ИЛИ_ДОМЕН_ТВОЕГО_VPS>:51820
AllowedIPs = 0.0.0.0/0, ::/0
PersistentKeepalive = 25
```

- **PrivateKey** — приватный ключ **клиента** (из `client_private.key` при генерации для этого клиента). Никакого ключа сервера сюда не подставлять.
- **PublicKey** в [Peer] — публичный ключ **сервера** (содержимое `server_public.key` или `wg show wg0 public-key` на VPS).
- **Address** — тот же IP, что в `AllowedIPs` на сервере для этого клиента. Указан **/32** (один адрес клиента), как в типовых рабочих конфигах; /24 на клиенте иногда ведёт себя хуже.
- **PresharedKey** — опционально. Если при добавлении peer на сервер ты сгенерировал ключ (`wg genpsk`) и добавил его в [Peer] на сервере, тот же ключ нужно добавить сюда в [Peer]. Строку можно удалить, если не используешь.
- **DNS** — 1.1.1.1, 1.0.0.1 (Cloudflare). Можно заменить на 8.8.8.8, 8.8.4.4 (Google) или другие.
- **Endpoint** — внешний IP или домен VPS и порт **51820**, без лишних пробелов, например: `82.117.84.212:51820`.
- **AllowedIPs = 0.0.0.0/0, ::/0** — весь трафик через VPN.
- **PersistentKeepalive = 25** — держит туннель живым за NAT; можно оставить.

Ключи вставлять **одной строкой**, без переносов и пробелов в начале/конце.

**Если не подключается** — проверь по шагам:
1. На сервере есть этот клиент: в `/etc/wireguard/wg0.conf` есть блок [Peer] с **публичным ключом этого клиента** и `AllowedIPs = 10.66.0.2/32` (IP совпадает с `Address` в конфиге клиента).
2. В конфиге клиента не перепутаны ключи: в [Interface] — только приватный ключ **клиента**, в [Peer] — только публичный ключ **сервера**.
3. Endpoint — верный IP или домен VPS и порт 51820; порт 51820 открыт в файрволе на VPS (`ufw allow 51820/udp` и при необходимости `ufw allow 22/tcp` перед `ufw enable`).
4. WireGuard на сервере запущен: `sudo wg show` показывает интерфейс wg0 и список peer’ов.

Готовый конфиг можно отдать другу как файл `.conf` или QR-код (удобно для телефона).

## 7. Диагностика: почему VPN не подключается

Проверяй по шагам — так можно понять, на каком этапе ломается связь.

### 7.1 На клиенте (телефон / ПК)

- **Приложение WireGuard**  
  Включи туннель и посмотри статус: «Подключено» / «Нет подключения» / текст ошибки. Если есть «подробности» или логи — открой их (часто пишут «handshake не прошёл» или «нет ответа»).

- **Проверка конфига на ошибки (ПК с WireGuard)**  
  На Windows/Linux/Mac при импорте или при включении туннеля приложение может показать ошибку (неверный ключ, лишний символ). Проверь, что ключи — одна строка, без переносов и пробелов в начале/конце.

- **Доступность сервера с клиента**  
  Нужно убедиться, что с твоего интернета до VPS доходят UDP-пакеты на порт 51820. С ПК (из той же сети, откуда подключаешься):
  - Онлайн-проверка порта: сайты вроде **portchecker.co** (порт 51820, UDP) — вводишь IP VPS. Или с другого сервера/хоста: `nc -u -v 82.117.84.212 51820` (должен «подключиться» по UDP).
  - Пинг до VPS: `ping 82.117.84.212`. Если пинг есть, но VPN нет — чаще всего блокируется именно **UDP 51820** (провайдер, роутер или файрвол на VPS).

### 7.2 На сервере (VPS)

Зайди по SSH и выполни по порядку.

**1. WireGuard запущен и интерфейс есть:**

```bash
sudo wg show
```

Должны быть строки `interface: wg0`, `public key: ...`, `listening port: 51820` и список `peer: ...` для каждого клиента. Если `wg0` нет — поднять: `sudo wg-quick up wg0`.

**2. Есть ли handshake с твоим клиентом:**

В выводе `wg show` у каждого peer есть строка `latest handshake`. Если там «(none)» или время много минут назад — handshake не прошёл или туннель мёртв. Значит:
- либо пакеты не доходят (сеть/файрвол),
- либо не совпадают ключи (на сервере должен быть **публичный ключ клиента** в [Peer], у клиента в [Peer] — **публичный ключ сервера**).

**3. Файрвол не режет UDP 51820:**

```bash
sudo ufw status
```

Должно быть правило `51820/udp ALLOW`. Если UFW включён и правила нет — добавить: `sudo ufw allow 51820/udp` и при необходимости `sudo ufw allow 22/tcp`, затем `sudo ufw reload`.

**4. Peer этого клиента действительно в конфиге:**

```bash
sudo cat /etc/wireguard/wg0.conf
```

Найди блок [Peer] с публичным ключом **этого** клиента. Проверь, что `AllowedIPs` совпадает с `Address` в конфиге клиента (например `10.66.0.2/32`).

### 7.3 Сводка: где искать причину

| Симптом | Где искать |
|--------|------------|
| В приложении ошибка при включении / «Invalid key» | Конфиг клиента: лишний символ в ключе, перепутаны ключи клиент/сервер. |
| «Подключено», но интернета через VPN нет | Сервер: `ip_forward=1`, в PostUp правильный интерфейс (eth0/ens3), iptables FORWARD и MASQUERADE. |
| Handshake (none) или очень старый | Сеть: UDP 51820 недоступен с клиента (провайдер/роутер) или закрыт на VPS (ufw/iptables). Либо неверные ключи. |
| Peer не виден в `wg show` | На сервере нет этого клиента в wg0.conf или конфиг не применён (перезапуск wg-quick@wg0). |
| Пинг до VPS есть, UDP до 51820 — нет | Файрвол на VPS или блокировка UDP у провайдера/сети. |

### 7.4 Разбор логов клиента (WireGuard для Windows)

Если в логах видно что-то вроде:

- `Sending handshake initiation to peer 1 (82.117.84.212:51820)` — клиент отправил запрос на handshake.
- `Receiving keepalive packet from peer 1 (82.117.84.212:51820)` — клиент **получил** пакет от сервера (keepalive).

**Вывод:** до сервера доходят пакеты (UDP 51820 открыт), сервер знает про этого peer и отвечает. Ключи и конфиг в целом совместимы. Ротация ключей (`Keypair 1 destroyed`, `Keypair 3 created`) через несколько минут — нормальное поведение.

Если при этом «VPN не работает», значит туннель, скорее всего, **поднимается**, а проблема в другом:

1. **Нет интернета через VPN** — на сервере проверь: `sysctl net.ipv4.ip_forward` (должно быть 1), в `PostUp` в wg0.conf указан правильный исходящий интерфейс (ens3/eth0), правила iptables FORWARD и MASQUERADE применяются. С клиента попробуй: `ping 10.66.0.1` (должен пинговать адрес сервера в VPN).
2. **Приложение показывает «Подключено», но трафик не идёт** — проверь маршруты и DNS на клиенте (в конфиге указан DNS = 1.1.1.1, 1.0.0.1). На сервере выполни `sudo wg show` — у этого peer должно быть недавнее `latest handshake` (секунды назад). Если handshake есть — ищи причину в форвардинге/NAT на сервере.

Если в логах **нет** строки `Receiving ... from peer` после `Sending handshake initiation` — пакеты от сервера не доходят до клиента (файрвол, NAT или блокировка UDP у провайдера).

После изменений на сервере имеет смысл перезапустить интерфейс: `sudo wg-quick down wg0 && sudo wg-quick up wg0`, затем снова включить туннель на клиенте и проверить `wg show` (появился ли handshake).

## 9. Удаление клиента

1. Открой `/etc/wireguard/wg0.conf`, удали блок `[Peer]` этого клиента.
2. Примени конфиг:
   ```bash
   sudo wg syncconf wg0 <(wg-quick strip wg0)
   ```
   или перезапусти `wg-quick@wg0`.

После этого этот ключ больше не сможет подключаться.

## 10. Безопасность

- Никому не отдавай **приватные** ключи сервера и клиентов.
- Конфиги и ключи храни с правами `600` (только владелец).
- Регулярно обновляй систему: `sudo apt update && sudo apt upgrade -y`.
- При желании смени порт с 51820 на другой и открой его в файрволе.

Дальше можно автоматизировать выдачу конфигов и учёт подписок — см. **SUBSCRIPTION_SYSTEM.md**.
